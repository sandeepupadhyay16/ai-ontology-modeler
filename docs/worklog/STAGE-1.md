|---|---|---|

| `CandidateConcept` | `candidate_concepts` — extracted entities/relationships/attributes, source turn, upper-ontology tag, dup/conflict status, accept/reject/merge decision | Matches the plan's field list as given. `dupTargetConceptId`/`mergeTargetConceptId` are separate nullable FKs to `Concept` (not reused as one field) since a candidate can be flagged as a possible-dup of one concept while later being merged into a different one during review. |

| `GlossaryDraft` | `glossary_drafts` — term, definition, linked ontology property, confirmation status | "linked ontology property" is modeled as two nullable FKs (`linkedConceptId`, `linkedRelationshipId`) since glossary terms can describe either a class (`Concept`) or a property (`Relationship`) in this schema — there's no single "property" table to point at. |
| `RuleDraft` | `rule_drafts` — condition/logic, linked ontology property, confirmation status | Same "which table is a property" ambiguity as above, but a rule's condition can read from a `Concept.Attribute` (datatype property) or a `Relationship` (object property). This is a deviation from the plan's literal `linkedPropertyId` (singular) — flagging it as a judgment call, open to being changed once Stage 8 actually elicits rules and we see what's really needed. |
| `OntologyVersion` | `ontology_versions` — git commit history, changelog | `changeSetId` is `@unique` (one version row per change set — 1:1) since the plan describes it as "linked to" a change set, not one-to-many. `gitCommitSha` nullable until Stage 10, as specified. |
| `Signoff` | `signoffs` — who approved what, when | As specified; `decidedAt` nullable (a routed-but-undecided signoff has no decision timestamp yet). |

## Decisions & rejected alternatives

1. **Plain `String` status/decision fields instead of Prisma `enum`.** The plan's spec uses the word "enum" for `dupStatus`/`decision`/`status`/`confirmationStatus`, but every existing status-like field in this schema (`BusinessSolution.status`, `DataMapping.status`, `CausalCycle.cycleType`, etc.) is a plain `String` with a `@default(...)`, not a Postgres-backed Prisma `enum`. I matched the existing convention rather than introducing the first enum type in the schema, per the plan's "match existing style" instruction. Allowed values are documented as inline comments next to each field. **Rejected alternative:** real Prisma `enum` blocks — more type-safe, but inconsistent with every other status field in the file, and enum migrations are more painful to extend later (adding a value is a schema migration; a documented `String` isn't). Worth revisiting once the code that writes these fields exists (Stage 2+) if type-safety at the Prisma-client boundary turns out to matter more than schema consistency.
2. **`RuleDraft.linkedPropertyId` as an untyped polymorphic reference, not a real FK.** See table above — there's no single "property" model to point a real foreign key at. Flagging this explicitly since it's a deviation from the letter of the plan and the one place I'm least confident is right; Stage 8 (rule elicitation) may reveal a cleaner shape once there's real code trying to populate it.
3. **`ConversationTurn.ordinal` uniqueness constraint.** Added `@@unique([sessionId, ordinal])`, not spelled out in the plan. Rationale: every downstream artifact's traceability depends on turn ordering being unambiguous; enforcing it at the DB layer now is cheap and additive, versus discovering an ordering bug later once Stage 2 is writing turns under concurrent requests.
4. **Cascade delete on `ontologyId`/`sessionId`/`changeSetId` FKs throughout.** Matches the existing repo-wide convention (nearly every FK in `schema.prisma` already cascades from its parent). Kept this deliberately consistent rather than introducing `Restrict`/`SetNull` semantics that don't exist elsewhere in the file.
5. **No new columns added to `Ontology`, `Concept`, or `Relationship`** beyond the back-relation array fields Prisma requires for the new relations (`modelingSessions`, `ontologyVersions`, `dupCandidates`, `mergeCandidates`, `glossaryDrafts`). These are metadata-only (relation declarations), not schema/data changes to those tables — confirmed no new column appears in the generated migration SQL for any pre-existing table.
